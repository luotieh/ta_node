# ta_node 无损存储与内存优化实施计划

状态：已实现无损内容存储、会话共享、按需读取、迁移和归档代码；本地回归与交叉编译已开展。上线迁移、现场容量配置、ARM 实机及 72 小时长稳验收尚需部署环境。实现细节与验证结果见 [storage-v2-operations.md](storage-v2-operations.md)。

目标：消除报文及会话全文重复保存带来的磁盘和内存放大，建立可恢复、可查询的数据归档机制，保持现有检测和业务接口正常工作。

## 1. 已确认的问题与适用范围

- `SQLiteQueue` 永久保留成功、待发、失败记录；重试上限和 PCAP 保留天数均不能限制数据库容量。
- 同一事务的后续报文会为此前各命中事件生成独立修订，每个修订携带累计会话全文。
- 原始报文、载荷、重组内容同时以 Hex、文本、兼容字段保存，多次复制同一数据。
- `cloneEvent`、`cloneExchange` 用 JSON 序列化/反序列化深拷贝，造成大量临时分配；推送按行数加载大对象也会放大内存。
- 本地构造的 80 个连续命中包约 85KB，生成 3,320 条待入库记录，累计 JSON 约 1.54GB；这是序列化复现，尚非服务器数据库测量。
- 现场文件为 `/data/ta_node-archive/event_queue.db.archived`。当前源码没有生成该后缀的逻辑，实施前确认是否仍被进程写入、是否与根目录处于同一文件系统。

本计划取代此前分析报告中“降低修订频率、合并未发送修订、裁减证据”的建议：这些措施会改变外部可见行为，不属于本次兼容改造。

## 2. 必须保持的兼容边界

1. 保持抓包配置、IOC/指纹匹配、逐包告警数量、触发条件和现有会话关联行为；不关闭 session，不减小 snaplen 或证据上限。
2. 保持 EventID、SessionID、TransactionID、ContextRevision、ContextFinal 及每个版本的字段语义，不丢弃或合并任何现有可见修订。
3. 同一个 EventID/revision 重试时，恢复出相同内容；历史版本不能引用可变的“最新会话”。
4. 保持 `packet_hex`、`payload_hex`、文本、重组结果、报文出现顺序及重传计数。相同字节的两次出现是两次采集，不能因去重而合并计数。
5. 保持现有推送接口、HTTP 头、JSON 字段、缺省/空值规则及成功判定；外部事件 schema 不因内部存储格式调整而改变。
6. 保持配置页面、现有 API 返回结构、推送记录、证据下载、PCAP 文件内容与路径契约。新的摘要和详情接口可追加，不能让旧接口突然缺少字段。
7. 保持失败重试和重试上限；超限数据仍可查询。保持原有至少一次投递语义，不承诺接收端缺乏幂等支持时实现恰好一次。
8. 兼容旧 JSON 队列及旧配置，增加独立 storage schema 版本。存储去重不改变检测器的事件身份生成方法。
9. 保持 Windows 离线回放、Linux AF_PACKET、可选 pcap、amd64/arm64/既有 ARMv7 目标和 vendor 离线构建能力。

JSON 验收以字段和值一致为准，保留 uint64 精度及字符串原文，不以对象键的排列顺序为功能标准。需要逐字节恢复的历史载荷保留原始 JSON 回退路径。

## 3. 存储模型

第一版优先在单个 SQLite 数据库事务中提交事件、证据引用、版本与 outbox；独立文件/对象归档通过后续明确的迁移协议处理。

| 逻辑实体 | 内容 | 约束 |
|---|---|---|
| evidence_content | 原始二进制或压缩块、codec、原始长度、哈希、校验信息 | 按完整内容去重；哈希命中后校验字节；冲突时保留不同内容 |
| packet_occurrence | 采集序号、时间、接口、链路类型、原始/采集长度、内容引用 | 每次出现独立记录；包内容相同不合并时间与计数 |
| event_base | 事件身份、触发信息、IOC/规则当时的元数据、触发报文引用 | 不能在读取时使用当前 IOC 元数据覆盖历史信息 |
| transaction_state | 事务公共信息、不可变证据序列和重组状态版本 | 不同事件共享同一份上下文；旧版本固定对应状态 |
| event_revision | EventID/revision、事务状态引用、事件专属增量、最终标志 | 保留每个可见版本；事件级字段与事务公共字段分开 |
| outbox | EventID/revision、原始入队次序、投递状态、重试计数与错误 | 一版本一投递状态，原子提交，不复制完整证据 JSON |
| archive_catalog | 历史段位置、格式、校验、迁移状态和可查询索引 | 归档完成校验并发布目录前，不回收源数据 |

### 3.1 二进制与派生表示

- 原始二进制保存一份，Hex 按需生成，不在每个事件内永久保存多份字符串。
- 载荷只有在确认是原始报文中的连续范围时才保存 offset/length；不满足时保存独立内容引用，不能凭空推导偏移。
- 重组保存现有算法的实际结果或可精确重建的片段关系，不借本次优化更改乱序、重叠、缺口处理。
- 记录表示算法版本，保留不能可靠重建的派生字段；升级解析器不得改写历史证据。
- PCAP 现有文件先保留兼容行为；第一轮收益集中在 JSON 数据库，不把“删除已有 PCAP”计为优化收益。

### 3.2 版本与快照

- 事务上下文按状态版本共享，事件修订只保留引用和事件专属变化。
- 使用周期性不可变快照加增量，限制恢复链长度；快照中的报文和重组内容仍用引用，避免整份证据再复制。
- JSON 深拷贝改为受控的不可变对象和显式必要复制；捕获源缓冲区在异步使用前必须转为自有内存，不跨生命周期借用可复用缓冲。
- 保留全部修订意味着元数据行数在极端场景仍可能达到 O(N²)。本次消除的是 O(N²) 个大内容副本及进一步的累计全文放大，不承诺全部开销变为 O(N)。

### 3.3 压缩与按需恢复

- 在去重后进行无损压缩，候选为纯 Go Zstandard；性能和目标平台验证前不锁定最终参数。新增依赖纳入 vendor。
- 第一阶段采用独立可解压内容单元。后续若引入约 1MiB 小块打包，应增加定位索引、单块解压上限和校验，不能需要解压整日文件才能读一包。
- 密文或小块压缩收益不足时使用 raw codec，不强制压缩导致膨胀。
- 还原最大长度来自已校验元数据，并受读取内存预算约束；损坏返回明确错误，不静默返回截断证据。
- 推送按需恢复原有完整 JSON。列表增加轻量摘要接口供新页面使用，旧完整接口继续兼容；新详情/范围读取接口使用鉴权、并发和读取大小控制。
- 内存预算限制同时驻留数据，不降低单条证据完整性；大于预算的单条事件通过流式编码、分块恢复或受控单任务处理，不能永久跳过。

## 4. 分阶段实施

### P0：现场基线与兼容测试资产

- 用只读脚本检查活动库和归档库、journal/WAL、实际配置、平均 JSON 大小、修订比例、已推送记录比例及进程打开的文件。
- 记录 CPU、RSS、Go heap/alloc、队列新增字节/秒、发送字节/秒、磁盘剩余量和 Linux 丢包指标。
- 将 `.analysis/queue_growth_repro.go` 固化为测试/基准资产，加入有代表性的 PCAP 场景，不使用生产密钥或向生产平台发送模拟事件。
- 固定回放时钟、规则数据和事件时间，输出旧实现黄金结果；覆盖重传、乱序、跨包、双向多次请求、EOF/FIN/RST/超时、多个 IOC 同时命中及已有截断边界。

交付：基线报告、黄金数据、可重复的存储/RAM/CPU 测量命令。后续收益以同一输入对比。

### P1：存储适配层和无损内容去重

涉及 `internal/queue`、`internal/event`，新增存储实现及 schema 管理。

- 引入 legacy/v2 存储后端，现有接口使用适配器保持兼容；新增 descriptor/单条读取接口供后续优化。
- 建立 content、occurrence、event、revision、outbox 表及必要索引，事务内完成引用和投递任务写入。
- 先对现有完整事件执行拆解并可逆恢复，验证 Hex、文本、空字段及丰富 IOC 元数据一致；不能恢复的旧格式走无损原文回退。
- 实现去重、codec 版本、校验、引用可达性校验；初始化或损坏失败必须清晰报错，不能返回空事件当作成功。
- 用单写入协调与有界读连接控制 SQLite 并发；是否采用 WAL 由平台测试确定，如启用则配套 checkpoint、长读事务和备份流程。

交付：可选 v2 后端，黄金事件还原一致，原子性与崩溃恢复测试通过。此阶段尚不能单独宣称解决上游 RAM 放大。

### P2：会话内部表示优化

涉及 `internal/correlation/tracker.go`、`internal/detector/engine.go`、`cmd/ta_node/main.go`。

- 将事务内容改为不可变共享对象和证据引用，直接向 v2 提交紧凑描述，避免先生成大 JSON 再拆解。
- 替换 `cloneEvent`/`cloneExchange` 的 JSON 深拷贝路径，保留必要的事件专属字段快照。
- 每个事件原有版本仍独立产生；统一事务状态供多个事件版本复用，不更改 Register/Observe/Flush 的外部事件序列。
- 内容落盘后按引用与缓存策略释放不再需要的内存；当前事务必要重组状态继续保留，不能提前丢弃影响后续分析。

交付：全量事件/版本对比通过，修订增长时不再持有大量相同证据副本，RAM/分配基准明显下降。

### P3：按需读取与发送内存控制

涉及 `internal/queue/inspect.go`、`internal/push/client.go`、`internal/server/http_server.go`。

- 队列先加载轻量任务描述，再按字节预算恢复和发送单条事件；兼容 `push_batch_size`、重试间隔、状态与顺序。
- 新页面使用摘要加详情读取，旧接口保持完整响应；归档后的现有可查询记录由统一读取层解析，不能直接绕过适配层查询旧 payload 列。
- 证据按报文或范围读取，报告总长度、范围、原始截断信息；展示分页不意味着证据丢失。
- 本次默认保持现有发送调度。连续排空、并发发送、退避策略属于可选后续变更，需验证接收端容量和顺序契约后再启用，不能把吞吐变化隐藏在存储改造中。

交付：平台无需改造即可接收原 JSON，现有页面/API/证据下载回归通过，超大事件不会因固定内存预算永久饿死。

### P4：可查询归档与容量治理

涉及存储后端、归档目录、配置、部署文档和健康指标。

- 将活动 outbox 与可查询历史的生命周期分开；已接收历史可以迁移到有容量的归档存储，不把成功标记等同于删除。
- 归档段应包含所需引用的闭包，或提供可靠内容位置目录。写入临时段、刷盘、校验、原子发布目录、确认查询和恢复成功后才允许回收源记录。
- 待发/重试超限数据保持持久化和可查询；若要迁移待发内容，outbox 引用必须在迁移切换中持续可恢复。首版优先只归档无待发依赖的数据。
- 引用回收受事务、活动读者和未完成归档保护，支持重启后恢复未完成的归档任务；保留可达性审计，避免错删共享证据。
- 设置活动库高低水位、归档容量监控、最低剩余空间阈值和操作告警；阈值不得触发静默删除或降低抓包长度。
- 对现有大库，删除只产生可复用空闲页，不承诺文件自动缩小；初次回收通过有充足空间的新库/分段迁移完成，禁止在满根分区原地执行大型 VACUUM。
- 永久证据保留不等于永久驻留根分区；只有外部归档容量持续可用，才能实现活动存储受控而历史不丢失。

交付：活动空间在约定保留窗口及归档条件下稳定；归档后查询、推送重试和证据恢复一致。

## 5. 配置与部署原则

- 新增配置与外部事件 schema 分开版本管理，建议项包括 backend、内容 codec、缓存字节预算、读取字节预算、快照间隔、活动容量高低水位、最低剩余空间和归档位置。
- 具体默认容量从目标机 RAM、磁盘及实测事件体积确定，不在未测量时假设统一 500GB 或固定线程数。
- 不新增默认丢弃策略；不自动删除超限失败记录，不缩短已有证据保留要求。
- legacy 配置可启动。v2 启用前做磁盘、路径、格式、归档能力检查，明确展示当前后端与迁移状态；不得假装启用成功。
- 归档目录与活动目录都应核验实际挂载点，避免把同一根分区下的不同目录当成容量隔离。

## 6. 历史数据迁移与回滚

1. 先清点活动进程、真实打开文件和 SQLite 日志模式。`.archived` 后缀本身不能证明文件静止或是完整备份。
2. 冻结的历史库在独立有空间的目标位置只读分批迁移，使用 ID 游标、断点、校验和迁移日志，不全量载入内存，不在根分区复制另一份 500GB 原文。
3. 对活动库，采用可验证的一致快照/备份及明确切换水位；迁移期间的新增、成功状态、失败计数都需追平，不能只同步新增 ID。
4. 最终切换需协调全部写入者，在事务边界暂停队列写入/推送、校验状态后切换；是否需要维护窗口或冗余节点由现场部署决定。现有单进程架构不能凭计划承诺重启期间无抓包间隙。
5. 旧库保留只读，迁移后新事件进入 v2；统一读取层支持兼容查询。归档记录保留原状态，不因导入触发重新发送。
6. 首选用同时支持两种存储的兼容版本回滚程序。旧二进制不能直接读 v2；如必须回退旧二进制，需导出切换后新增及变化的数据为旧格式，并验证容量、状态和水位后再切换。
7. 任意阶段回滚都不允许丢弃切换后的新事件，也不能重新发送全部已确认记录来“恢复”。

初期生产不长期双写完整旧格式，避免在容量危机中加倍消耗；影子对比在实验环境或有明确空间预算的受控样本中进行。

## 7. 验收标准与测试矩阵

| 维度 | 发布门槛 |
|---|---|
| 检测与事件兼容 | 黄金 PCAP 下 EventID/版本序列、所有字段值和告警数量 100% 一致；使用类型安全比较避免大整数丢精度 |
| 原始证据 | 已捕获字节、出现次序、时间、原有截断标志、重传计数和 PCAP 下载结果一致；去重不改变出现次数 |
| 存储收益 | 80 包高重复基准新落盘总量（含索引、元数据、日志及附加证据）目标较旧实现下降至少 90%；需实测，不能以 JSON 估算冒充落盘收益 |
| 普通流量 | 加密/高熵、无重复、小包/大包场景单独测量；压缩收益不足自动选择 raw；实测 CPU 与延迟不出现不可接受回退 |
| 内存 | 固定活跃会话和读取并发下，RSS/heap 随历史总量增加不持续增长；分配量、峰值和缓存预算可解释；高重复基准峰值目标下降至少 50%，以测量确认 |
| 推送 | 每版本状态独立，成功判定/重试上限兼容；HTTP 超时、2xx 后本地状态写入前崩溃等情况保持原至少一次语义 |
| 崩溃与损坏 | 在内容写入、引用提交、状态更新、归档发布、回收各边界中断后恢复，无已提交任务悬空；损坏可检测，原件未校验不删除 |
| 生命周期 | 超限失败数据不被误删，共享证据在最后引用消失前不回收；归档失败不破坏原数据；归档后旧接口仍可读取 |
| 迁移回滚 | 大库分批迁移可恢复；新增与状态更新追平；回滚不丢切换后事件，不重置重试次数 |
| 长稳运行 | 在双方约定流量和归档可用条件下至少 72 小时运行；活动空间、内存、推送延迟和丢包率达到目标，告警可用 |
| 平台 | Windows 测试/回放、Linux 实时抓包及目标 ARM 运行验证；单元测试、并发测试、集成故障测试和离线构建通过 |

保留所有完整版本、继续推送全部 JSON 时，网络输出及轻量修订元数据仍可能很大，应单独容量测算。上游产生速度长期高于推送/归档速度、或者所有存储耗尽时，固定资源下无法同时保证无限接收、永不丢失和永久保留；必须有足够持续容量、及时扩容和可见的故障处置，不用“阻塞抓包”伪装成无损。

## 8. 推荐交付拆分与讨论项

按 P0 → P1 → P2 → P3 → P4 推进，每阶段独立评审和验证；完成 P1/P2 只代表去重和内存优化，P4 完成且归档容量落实后才算解决长期填满磁盘问题。

建议先确认以下部署约束，P0 和兼容测试可独立开始：

- 历史是否永久保留，以及允许采用独立磁盘、NAS 或对象存储中的哪种归档目标。讨论期间按“全部保留、不自动丢弃”设计。
- 目标节点架构、RAM、活动盘/归档盘容量、实际持续流量和允许的故障恢复时间。
- 发布是否允许短维护窗口；如要求采集无间断，是否存在冗余采集节点或上游可回放机制。
- 是否有外部程序直接查询 `event_queue.payload`。若有，将其纳入兼容接口/迁移清单，不可直接删旧表。
