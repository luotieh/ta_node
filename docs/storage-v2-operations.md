# 无损存储 v2：部署、迁移、归档和回滚

## 行为与兼容性

新版默认将**新写入**的事件保存为内容寻址快照：原始 Hex 转回二进制，按 4096 字节分块；内容以 SHA-256 定位并逐字节验证复用。字符串、报文元数据、会话快照通过不可变引用共享。使用 Go 标准库 zlib 无损压缩，压缩更大时保存原文，无新增运行库或联网依赖。

所有 EventID、revision 和报文出现记录保留。Hex/文本/重组字段在读取和推送时按旧格式恢复，不降低 snaplen、证据长度、规则数量或会话功能。重传的相同字节可共享，采集次数、时间和顺序不合并。存储格式版本为 2，对外事件 Schema 仍为 1.6。

实现使用不可变内容图快照及共享二进制块，代替计划中单独的逐字段增量日志：没有需要从版本 1 回放的长增量链，已有版本和内容节点不更新。修订元数据数量仍可能为 O(N²)，但不再逐行复制累计报文全文。

旧 JSON 行可与 v2 行混合读取。启动不会重写历史数据，也不会为旧大表自动执行全表索引构建。直接访问 `event_queue.payload` 的外部 SQL/脚本必须调整：新行是内部引用，不是完整事件 JSON。业务应使用节点 API；必须依赖旧 SQL 时先使用 `storage.backend: legacy`，再安排迁移。

`backend: legacy` 只控制新写入格式，**不会把已有 v2 数据转换回旧格式**。旧二进制不能直接读取包含 v2 行的数据库。

## 配置

```yaml
storage:
  backend: "v2"
  archive_dir: ""                # 填写已核实容量的归档盘绝对路径后才启用
  archive_after_hours: 24         # 成功接收后在活动库驻留多久；不是删除历史
  maintenance_interval_sec: 60
  archive_batch_size: 100         # 每次最多 1000 条，保留全部修订
  high_water_bytes: 0             # 活动库已用页的高水位；0 表示不设置
  low_water_bytes: 0              # 必须小于非零高水位
  min_free_bytes: 0               # 活动盘/归档盘剩余空间警戒值
  shards: 4                       # 哈希分片并发存储的库文件数；0/1 为单文件
```

### 哈希分片并发存储

`shards: N`（2~64）把队列写入按 `FNV-1a(event_id)` 路由到 N 个独立的 v2 数据库并发写入，避免高速率场景下所有写事务串行排队。布局：分片 0 即原 `events.db` 本身，分片 i（i>0）为同目录下 `events.db.shard<i>`。

- **兼容**：已存在的单文件库直接作为分片 0，其中待发记录照常读取推送，无需迁移；同一事件的全部上下文修订始终落在同一分片。
- **读取自动合并**：`/api/v1/push/logs`、`/api/v1/push/event`、`/api/v1/storage` 均按基础路径自动发现 `*.shard<N>` 兄弟文件并合并结果（`/api/v1/storage` 的 `shards` 字段报告分片数）。
- **归档**：维护线程对每个分片独立归档到同一归档目录，段文件名为 UUID，不会冲突。
- **离线迁移**：`ta_queue` 按单文件工作；分片部署需对每个分片文件分别执行。
- **注意**：写入路由只保证"同事件同分片"；运行中**不要修改分片数**，否则同一事件可能写入不同分片产生重复。需要调整时用 `ta_queue` 导出合并后重建。

配置需重启生效。高水位达到后，可以提前归档已推送记录，低水位恢复正常保留窗口。待发、失败和超过重试上限的数据不自动删除。阈值告警只报告问题，不静默丢弃证据。每轮归档数量/间隔应结合现场写入速率与推送确认速率测算；配置不当仍可能积压。

**归档目录为空时只启用去重，不会自动限制历史总容量。** 不默认使用 `/data`，因为目录名不能证明它是独立挂载点。上线前检查 `findmnt -T 归档目录` 和 `df -h`。成功历史可外移后，活动内容页可复用，但轻量的归档定位/去重索引仍随历史记录数增长，需纳入容量规划。

源盘同样要保留数据库事务、回收和运行日志的空间，归档不能在已满盘条件下保证完成。无限待发数据或无限历史必须有相应存储容量；这一实现不提供超限丢弃策略。

## 新增读取入口

- `GET /api/v1/push/logs`：保持现有完整日志返回。
- `GET /api/v1/push/logs?summary=1`：省略报文内容的摘要，页面默认使用。
- `GET /api/v1/push/event?event_id=事件ID&revision=版本`：完整指定版本，读取活动库或归档。
- 同上增加 `offset=起始字节&length=字节数`：只读取触发原始报文的相应范围，每次最多 65536 字节。v2 按块读取，不加载无关会话内容；旧 JSON 需先读取旧行。
- `GET /api/v1/storage`：活动库分配页、可复用页、文件字节、磁盘剩余量、归档段数量。

新增完整详情、范围及容量接口要求已有 `server.token`（若配置）；未设 Token 时沿用本机服务约定。证据详情最多两个并发读取。旧完整日志接口保持兼容，新页面展开时才取完整数据，已有 Token 输入用于详情请求。

推送每轮仍按原批量数、原顺序和原间隔执行，但先读取任务 ID，再一次恢复一条完整事件，避免在 RAM 同时驻留整批证据。每次恢复有最多 8MiB 的内容缓存，读取结束即释放；完整事件本身及网络序列化仍需要对应内存，不会因超过缓存预算而截断。

只读离线检查也可以使用 `ta_queue --inspect --source 数据库路径`，无需 `--offline`，支持旧格式、混合格式和归档查询。此前 Python 诊断脚本遇到 v2 会明确提示使用此工具，避免把内容引用误判为缺少来源。

## 500GB 历史库迁移

迁移工具只支持**明确停止写入且已完成 checkpoint 的一致源库**。不宣称支持在线复制变动中的旧库。现有 `.archived` 后缀不保证文件已停止写入，先用 `lsof` 确认。源文件与目标文件不可相同。

构建工具（portable 与 ARM 离线构建脚本也会生成对应二进制）：

```sh
go build -mod=vendor -o ta_queue ./cmd/ta_queue
```

将目标放在有充足空间的独立卷，使用实际冻结文件：

```sh
./ta_queue --offline \
  --source /data/ta_node-archive/event_queue.db.archived \
  --destination /mnt/queue-volume/event_queue-v2.db \
  --backend v2
```

- 源库只读，不修改或删除；逐条复制、验证，并原子提交数据与断点。
- 逐个处理归档段，分别保存断点，不同时打开全部段；使用原始 ID 写入，归档段的处理顺序不会改变投递顺序。
- 保留所有事件版本、顺序 ID、投递状态、错误和重试次数；不会把历史成功记录变为待发。
- 大整数不经 float64 转换；未知历史字段保留。v2 的自包含归档段也参与导出。
- Ctrl+C 后可用相同参数继续；必须保持源文件及其归档段不变。恢复前校验文件路径、大小和修改时间，并核对后端。
- 源存在非空 WAL 时拒绝迁移，先准备一致且 checkpoint 完成的离线备份，**不要手工删除 WAL/SHM**。
- 输出 verified 后才能切换节点的 `event.queue_db`。旧库先保持只读，验收后由操作人员依据备份保留策略处理，工具不替你删除。
- 启动新版后会写入 v2，不可把旧二进制直接指回该库。

初始 500GB 文件不会因删除记录立刻变小。迁移到新库可以紧凑重写且保留原件；不在已满根分区执行全库 VACUUM。

迁移程序要求源和目标均无其他写入者，`--offline` 是这一操作约束的显式确认，并非远程停止服务功能。单节点重启/切换存在抓包间隙；需要无间断采集时须由冗余节点或上游可回放设施保障。

## 归档原子性与恢复

归档先记录复制意图，再将一批已推送数据连同全部引用内容写成独立 SQLite 段，刷盘并逐条验证内容与状态，最后用源库同一事务提交归档目录、定位索引及活动记录删除。共享内容只有不存在任何事件根或父引用时才回收。

复制中崩溃：源记录仍在。启动维护任务或下一次归档会检查复制意图，清理本节点未发布的副本并重试；若已发布，则保留归档并清理意图。已发布段丢失会报错，不静默跳过证据。归档目录必须仅由这一节点写入，节点数据库也必须只有一个运行进程作为写入者。

活动读者使用一致读事务，避免归档回收期间读到悬空引用。SQLite 不自动缩小活动文件，但释放页会被后续写入复用；库文件大小和实际已用页应分开监控。

不要移动/修改已登记的归档段；当前目录保存绝对路径。整体迁移时需保持路径或使用 `ta_queue` 汇总导出到新库再切换。备份必须包括活动库、归档目录及其全部归档段。

## 回滚

优先回滚到仍支持 v2 的兼容程序版本。必须使用原旧二进制时，先冻结当前库，完整导出旧格式：

```sh
./ta_queue --offline --source /mnt/queue-volume/event_queue-v2.db \
  --destination /mnt/rollback-volume/event_queue-legacy.db --backend legacy
```

恢复旧格式会再次放大空间，必须提前测算目的盘容量。导出包括当前库已登记的归档历史，保留状态和切换后新增数据。不得只启动升级前旧库，从而遗漏升级期间事件。

## 验证记录与尚需现场验证的项目

- 原实现固定 20 包事件序列 SHA-256：`45c82c628146ecc0cdae1b3096fadb9dd7db0381ba350ded6b83f6ac68be49d8`；新实现所有版本恢复结果相同。
- 实测 20 包/230 版本：旧 SQLite 28,360,704 字节，新 SQLite 1,208,320 字节，下降 95.74%。
- 实测 80 包/3,320 版本：旧 SQLite 1,542,705,152 字节，新 SQLite 14,880,768 字节，下降 99.04%。这是构造的高重复流量，不代表所有生产流量的压缩率；附加管理表可能使文件多若干 SQLite 页。
- 同一 20 包生成链路的 Go 累计分配量从 117,355,800 降至 34,783,768 字节，约减少 70.4%；这是累计分配，不是 RSS/峰值内存，也不包含数据库读取。
- 单元/集成覆盖混合格式、全部版本恢复、损坏检测、共享引用回收、归档后查询、失败归档保留原件、迁移恢复/旧格式导出、摘要不解码证据、跨块范围读取、详情鉴权和旧页面保存配置兼容。
- 本地全量 `go test -mod=vendor ./... -count=1`、`go vet -mod=vendor ./...` 通过；Windows 二进制端到端检查及 Linux amd64/arm64/ARMv7 交叉编译通过。新增迁移回归覆盖多个归档段的交错 ID、归档文件误作目标保护及空库 ID 水位保留。
- 可使用 `python scripts/verify_storage_v2.py --node 节点程序路径 --queue-tool 迁移工具路径` 重跑隔离端到端检查，验证旧库迁移、启动、鉴权、详情、范围和配置保存；仅创建临时文件和访问本机 HTTP 服务。
- 80 包实际落盘回归通过环境变量 `TA_STORAGE_BENCH=1 go test -mod=vendor ./internal/queue -run TestSessionStorageGoldenAndDiskReduction -count=1 -v` 运行；默认测试使用 20 包。
- 生产 PCAP 的性能收益、采集丢包率、部署盘容量、ARM 实机行为和 72 小时长稳测试仍需目标环境验证。交叉编译不替代实机测试。本机缺少 CGO/C 编译器，race 检查需在具备工具链的 CI/目标测试机运行。

本次不更改已知 HTTP 解析、会话判定或 PCAP 归档行为，避免把检测语义变化混入存储兼容改造；这些问题应另行修复并建立对应回归。
